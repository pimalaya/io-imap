# Response budgets, and COPYUID kept as ranges

Six findings of the family audit of 2026-11-13, each a place where the server, or the sender of a mail, chose what the client spends.

- **Collected responses (IMAPA-03).** `ImapSend` charges each collected data and untagged status response to a public `budget: ImapSendBudget` (responses and summed wire octets) and fails with `ImapSendError::ResponseTooLong`. Both bounds are kept: a response costs several times its wire size once decoded, so octets alone leave the count free, and a count alone leaves the size free. The default (16,777,216 responses, 1 GiB) is meant never to refuse a legitimate exchange, a whole-mailbox `FETCH 1:* (UID FLAGS)` returning one response per message. `ImapSendBudget::PRE_AUTH` (1024 responses, 1 MiB) is set by CAPABILITY, ID, LOGIN and the six AUTHENTICATE coroutines, on the command and on each continuation; it is looser than the handful of lines these need because CAPABILITY and ID also run later in a session, where unsolicited mailbox updates count. `ImapRaw` gets `max_response_len` (1 GiB) and `ImapRawError::ResponseTooLong`. The budget is a field rather than a constructor option to leave the three `ImapSend` constructors and their sixty call sites alone; the wrapping coroutines expose no way to change it.
- **COPYUID (IMAPB-02, IMAPB-09).** `ImapCopyUid` is now a struct: `uid_validity`, `source` and `destination` as `Vec<RangeInclusive<NonZeroU32>>` in wire order, `pairs()` and `count()`. Nothing is expanded or sorted, so `1:4294967295` costs one range and the positional pairing of RFC 4315 section 3 survives. A COPYUID whose sets differ in length gives `None`: the server completed the copy, so failing the command would invite a retry and a duplicate. COPY and MOVE return `Option<ImapCopyUid>`.
- **FETCH streams (IMAPB-14).** `ImapMessageFetchStream::new(id, opts)` takes `ImapMessageFetchStreamOptions` (`uid`, `max_literal_len`, `size`) and fails with `LiteralTooLong`; `ImapClientStd::fetch_body_stream` keeps its signature and now applies the 100 MiB default. The batch stream remembers the UIDs it streamed, removes each from `sizes` and fails with `UidRepeated` on a repeat. It still accepts one body per distinct UID outside the request.
- **Streamed APPEND (IMAPA-14, IMAPB-19).** `ImapClientStd::append_stream` fails with `ImapClientError::MessageTooLong` before writing when the length exceeds `u32::MAX`, instead of announcing the truncated length and streaming the whole source.
- **Base subject (IMAPB-11).** Once `strip_leader` fails, no leader can follow the blobs it walked, so they are stripped in one pass: two `strip_blob` calls per blob (the test allows three) where 1000 blobs took 502,502. The old and new loops agree on the 1,111,111 strings of up to six tokens among `[a]`, `re`, `:`, a blank, `x`, `[`, `]`, `fwd`, `(fwd)` and `[fwd:` (a throwaway differential test, not kept). The regression test counts calls through a thread-local probe compiled under `cfg(test)` only.

Breaking: the shape of `ImapCopyUid` and the return type of COPY and MOVE (coroutines and client methods), `ImapMessageFetchStream::new`, and the new variants of `ImapSendError`, `ImapRawError`, `ImapMessageFetchStreamError`, `ImapMessageFetchStreamBatchError` and `ImapClientError` for exhaustive matches.

Existing tests changed: the COPY and MOVE tests that pinned sorted `Vec<u32>` sets (`success_with_copyuid_returns_uids`, `success_with_uidvalidity_zero_returns_uids`, `lenient_copyuid_takes_only_uidvalidity_zero`, `success_with_untagged_copyuid_returns_uids`) assert the same UIDs as pairs; the FETCH stream tests build their coroutine from options.

Fuzzing: the `response` target drives COPY and MOVE with the oracle that a COPYUID pairs as many UIDs as it counts, and answers the tag of the single body stream, which it never did, so that stream was not fuzzed until now. 430,576 runs in 46 seconds, no crash; three hand-written inputs (a COPYUID over the whole UID space, an untagged COPYUID on MOVE, a body announcing 4 GiB) replayed clean. fuzz/Cargo.lock gained mime-rs and its dependencies, which the fuzz build needed since the crate depends on it.

Capabilities moved: coroutines (budget requirement added), message-sort (linear base subject added), message-copy and message-stream (new spec files).

Verified: every new test failed first, against the previous code or the previous shape (`capability::tests::endless_untagged_run_returns_too_long_error` yielded `WantsRead`; the COPYUID tests saw 3,000,000 elements, `[3, 5]` for `5,3` and a mismatched pair accepted; `fetch_stream::tests::literal_over_max_fails` saw `WantsStream { len: 4294967295 }`; `fetch_stream_batch::tests::repeated_uid_fails` saw both bodies; `client::tests::append_stream_over_u32_fails_before_writing` saw `APPEND INBOX {100}` written; `sort::tests::base_subject_work_is_linear_in_blobs` saw 502,502 calls). The budget tests in src/send.rs and src/rfc3501/raw.rs set fields that did not exist before. `cargo test --all-features` passed (277 unit, 11 integration, 47 doc tests); `cargo clippy --all-features --all-targets -- -D warnings` clean but for the pre-existing one-element range array in src/watch.rs; `cargo build --no-default-features` builds; `cargo doc` has no broken link.
