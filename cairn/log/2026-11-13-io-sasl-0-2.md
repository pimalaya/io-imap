# The mechanisms run on io-sasl 0.2

io-sasl 0.2.0 was published on 2026-11-13 and io-imap moves to it, as a dependency and as a dev-dependency. One version of it remains in the graph. The only line that stopped compiling was `SaslScramSha256::new(creds)`, which now takes a `SaslScramOptions`.

- **Iteration bounds (family audit of 2026-11-13, IMAPA-02).** A SCRAM server chose how long one resume computes: the iteration count had no bound, here or in io-sasl. io-sasl 0.2 bounds it, 4096 to five million by default, and refuses a count outside the window before the derivation runs. The bounds are reachable from this crate as the io-sasl struct itself, in a `scram` field of `ImapAuthScramSha256Options` and of `ImapSessionOpenOptions`, the second one present with the `scram` feature only. The std client needed nothing of its own: `auth_scram_sha256` takes the first, `connect` the second through its session options. A refused count takes the path of any challenge the mechanism refuses: `*`, the tagged reply, then the error.
- **Preparation.** io-sasl 0.1 prepared the PLAIN and SCRAM credentials under its `saslprep` feature, which this crate, depending on it without default features, left off: they went out, or were derived from, as given. The feature is gone and preparation is unconditional. This is a behaviour change on the wire: a password SASLprep alters (a compatibility form, a soft hyphen, a non-ASCII space) is now sent prepared, which is what a server that prepared it when it was set expects, and which fails against one that stored it raw. A credential holding a prohibited code point, a NUL in a PLAIN field included, fails with `Preparation` before anything is written. unicode-normalization enters the tree without std: `cargo tree --no-default-features --features scram -e features,no-dev` still lists no `std` feature and no rand.
- **Nonce.** io-sasl 0.2 refuses a client nonce shorter than 18 bytes or outside the alphabet of RFC 5802 at its first resume. `EmptyNonce` stays, raised by the constructor; the rest fails the first resume with `Mechanism(InvalidNonce)`, before the tag is asked for. `ImapClientStd::connect` draws 24 alphanumerics, as before.
- **Errors.** The io-sasl error enums carried by the `Mechanism` variants gained variants (`InvalidNonce`, `IterationCountTooLow`, `IterationCountTooHigh`, `MandatoryExtension` for SCRAM, `InvalidCreds` for OAUTHBEARER and XOAUTH2), and the two `Preparation` variants are always present.
- **A server announcing fewer than 4096 iterations is refused by default.** A caller facing such a server lowers `min_iterations`.

Breaking: the io-sasl dependency is 0.2 and its types are in this crate's public API; `ImapAuthScramSha256Options` and, with `scram`, `ImapSessionOpenOptions` gained a public field, which breaks a struct literal naming every field; PLAIN and SCRAM-SHA-256 prepare their credentials.

No existing test changed. io-oauth stays at 0.4, a dev-dependency of the provider tests, and brings io-http 0.6 with it; io-imap has no dependency of its own on io-http.

The proposal of uncopied-literals-and-incomplete-listings lists the `saslprep` feature as not enabled: that line is history, the feature no longer exists.

Capabilities moved: coroutines (two requirements added, one modified).

Verified: `iteration_count_above_the_ceiling_cancels_without_deriving` and `scram_iteration_ceiling_reaches_the_mechanism`, written with the options field present but not handed to the mechanism, both failed on the client-final-message written where `*` was expected. `short_nonce_fails_the_first_resume` and `ir_password_goes_out_prepared` were not run against io-sasl 0.1. `cargo test --all-features` passed (334 unit, 12 integration, 47 doc tests); `cargo clippy --all-features --all-targets -- -D warnings` clean; `cargo build --no-default-features` builds, as do `scram` alone, `client` alone and a TLS feature without `scram`.
