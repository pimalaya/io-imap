# Modified UTF-7 runs on base64-codec

The base64 crate gave way to base64-codec 0.1, as the family decided on 2026-11-03. Its only production use is the modified UTF-7 codec of mailbox names in src/rfc3501/mailbox.rs (RFC 3501 5.1.3); the SCRAM-SHA-256 tests use it for their fixtures. The encoder writes unpadded base64 and maps `/` to `,` byte by byte, which also drops an `unsafe` block.

The decoder needed more than a swap. The old one tried the strict padded engine then the strict unpadded one, and re-emitted a shift either refused verbatim. base64-codec decodes leniently, skipping blanks and accepting non-zero trailing bits and lone padding, so a naive swap decoded `&AGF-`, `&AG E-`, `&=-` and `&AGF=-` where the old code kept them. Strictness matters here beyond fidelity: a name decoded from a non-canonical form encodes back to a different one, which the server does not know. The decoder now accepts a shift only when its bytes encode back to the payload, padded when the payload is, which is exactly what the two strict engines accepted.

A scratch differential run compared the old and new `decode` over every shift payload of up to 6 bytes from `AQgw+/,= !-`, inside a name and at its end: 3,897,434 inputs, no difference (181,560 before the canonical check). `encode` matched on the reference names.

imap-codec and imap-types still depend on base64 0.23, so the crate stays in io-imap's tree until they move.

Capabilities moved: none.

Verified: `decode_keeps_non_canonical_shifts_verbatim` passes and fails against the naive swap; `cargo clippy --all-targets --all-features` clean but for the pre-existing one-element range array in src/watch.rs, the `chunks_exact` warning in the touched decoder fixed through `as_chunks`; `cargo test --all-features` passed; `--no-default-features` and the fuzz crate build.
